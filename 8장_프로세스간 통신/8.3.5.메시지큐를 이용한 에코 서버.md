# 8.3 메시지 큐 (Message Queue) — 8.3.5 메시지 큐를 이용한 에코 서버

## 1. 구조 개요

메시지 큐를 이용한 UDP형 에코 서버는 **두 종류의 프로세스**로 구성된다.

| 프로세스 | 역할 | 실행 개수 |
|---------|------|----------|
| **REQ_RECV_PROC** | 에코 **요청을 수신**하여 메시지 큐에 넣고 다음 요청 대기 (반복) | **1개** |
| **RES_SEND_PROC** | 메시지 큐에서 읽어 클라이언트에게 **에코 응답** (반복) | **여러 개** |

- 여러 개의 `RES_SEND_PROC`가 **하나의 메시지 큐로부터 경쟁적으로** 메시지를 읽음
- 메시지 큐가 **내부적으로 동기화를 맞춰주므로 별도의 동기화 코드는 불필요**

### 여러 송신 프로세스 생성
```c
#define RES_SEND_PROC "./res_send"

void fork_and_exec(char *key, char *port) {
    pid_t pid = fork();
    if (pid < 0) errquit("fork fail");
    else if (pid > 0) return;

    execlp(RES_SEND_PROC, RES_SEND_PROC, key, port, 0);
    perror("execlp fail");
}
```

## 2. 전달 메시지 구조

```c
typedef struct _msg {
    long               msg_type;
    struct sockaddr_in addr;                 // 에코 메시지를 보내온 클라이언트 소켓 주소
    char               msg_text[MAX_BUFSZ];  // 에코 메시지
} msg_t;
```

> UDP이므로 어느 클라이언트에게 응답할지 알기 위해 **클라이언트 소켓 주소(`addr`)** 를 함께 전달한다.

---

## 3. REQ_RECV_PROC 동작

메시지 큐와 소켓을 생성한 후, `recvfrom()`으로 클라이언트 메시지 도착을 대기한다.
도착하면 `msgsnd()`로 메시지 큐에 넣고 루프를 반복한다.

```c
pmsg.msg_type = 1;                       // 메시지 타입은 1로 설정
size = sizeof(msg_t) - sizeof(long);     // msg_type(long) 제외한 크기

while (1) {
    puts("Server waiting...");
    nbytes = recvfrom(sock, pmsg.msg_text, MAX_BUFSZ, 0,
                      (struct sockaddr *)&pmsg.addr, &len);
    pmsg.msg_text[nbytes] = 0;

    // 메시지 큐에 쓰기
    if (msgsnd(msqid, &pmsg, size, 0) == -1)
        errquit("msgsnd fail");
}
```

## 4. 관련 프로그램

| 파일 | 역할 |
|------|------|
| `msgq_echoserv.c` | 에코 메시지를 수신하여 메시지 큐에 넣음 (REQ_RECV_PROC 생성 코드 포함) |
| `res_send.c` | 메시지 큐에서 에코 메시지를 읽어 응답 (RES_SEND_PROC) |

- `RES_SEND_PROC`는 `exec` 호출 시 인자로 넘어온 **msgq key와 port 값**으로부터
  해당 메시지 큐의 키와 포트 번호를 얻는다.

---

## 5. 실행 결과 — 응답 프로세스 PID가 1씩 증가하는 이유

- 한 프로세스가 계속 메시지 큐를 읽는 것이 아니라,
  **여러 프로세스가 순서대로** 에코를 처리한다.
- 이유: 커널의 **프로세스 스케줄링 알고리즘**이 프로세스들을 공정하게 실행시키기 위해,
  **최근에 실행한 프로세스의 우선순위를 낮게** 책정한다.
  → 같은 프로세스가 연속으로 CPU 서비스를 받지 않게 되어, 응답을 처리하는 PID가 순환된다.

---

## 정리

- 구조: **수신 프로세스 1개(REQ_RECV)** + **송신 프로세스 여러 개(RES_SEND)**
- 여러 송신 프로세스가 하나의 큐에서 경쟁적으로 읽으며, **큐가 동기화를 보장**(별도 동기화 코드 불필요)
- UDP라서 메시지 구조에 **클라이언트 주소** 포함
- `msgsnd` 크기는 `sizeof(msg_t) - sizeof(long)` (msg_type 제외)
- 응답 PID가 순환되는 것은 **공정성을 위한 커널 스케줄러의 우선순위 조정** 때문
